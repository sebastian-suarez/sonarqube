# Spec: sonarqube-platform

Version: 4
Status: verified

## Problem

The user wants SonarQube Community Build for their own repositories, used both from GitHub Actions and from local checkouts in `~/Projects`. No server exists yet. Running one all the time costs about $20–26 a month in compute alone, but use is occasional (estimate: about 30 hours a month). The service should therefore cost close to nothing while idle. It should start only when a caller who proves they're legitimate needs it, and survive the loss of a Spot instance or of capacity in an Availability Zone by starting again in another AZ.

## Scope

In:

- OpenTofu under `infra/`. A `bootstrap/` root creates the state bucket. The main root owns:
  - the VPC, and VPC Block Public Access exclusions for its public subnets
  - subnets in every us-east-1 AZ
  - the Spot Auto Scaling group and its launch template
  - IAM
  - Aurora Serverless v2
  - SSM parameters
  - the AWS Budget
  - the Resource Group
  - the Cloudflare Tunnel, DNS record, Worker script, route and secrets
- The Worker source and its tests under `worker/`.
- The instance boot template and the idle checker, with its tests, under `instance/`.
- The reusable workflow `.github/workflows/sonarqube-scan.yml` and the caller example `docs/caller-workflow.yml`.
- `scripts/wake.sh` (wake and wait), `scripts/scan.sh` (local scans) and `scripts/onboard.sh` (opting a repo in).
- `README.md`: setup, onboarding, waking, local scans, upgrades and teardown.

Out:

- Other repositories' files. `onboard.sh` sets secrets and prints a snippet; it never commits, pushes or opens PRs.
- `~/Projects/aws`.
- Account- and organization-level AWS settings. Creating the `sonarqube` member account, granting its SSO access, and keeping the `Project` cost allocation tag active in the management account are done outside OpenTofu.

Non-goals:

- High availability. At most one instance runs at a time, and downtime while waking or after an interruption is accepted.
- Branch or PR analysis (not available in Community Build).
- Swift, C and C++ analysis (not in Community Build).
- A baked AMI.
- Automatic SonarQube upgrades.
- CI/CD for this infrastructure.
- Cloudflare Access.
- Users other than the owner.
- On-demand fallback when no Spot capacity exists.

## Definitions

- **AWS profile**: `sonarqube`, the IAM Identity Center profile for the dedicated member account `368861736633`. Every OpenTofu root and every local `aws` command names it explicitly. Nothing falls back to the default profile, which points to the management account.
- **H**: `sonar.sebastiansuarez.dev`. **Base URL**: `https://sonar.sebastiansuarez.dev`.
- **Group**: the Auto Scaling group named `sonarqube` in `us-east-1`.
- **Wake key**: a random string of at least 32 characters, generated by OpenTofu and stored in `/sonarqube/wake-key` and as the Worker secret `WAKE_KEY`.
- **Session key**: 32 random bytes, base64-encoded, generated by OpenTofu. It is stored in `/sonarqube/jwt-secret`, as the Worker secret `JWT_SECRET`, and as SonarQube's `sonar.auth.jwtBase64Hs256Secret`.
- **Wake credential**: a request carries one when either holds:
  - an `X-Sonar-Wake-Key` header equals the wake key (constant-time comparison)
  - a `JWT-SESSION` cookie is a JWT with header `alg` = `HS256`, an HMAC-SHA256 signature that verifies against the base64-decoded session key, and an `exp` claim in the future
- **Origin down**: the Worker's fetch to the origin throws, or returns 502, 503, 504 or 530.
- **Activity**: a SonarQube access-log line where SonarQube authenticated the user (its `%reqAttribute{LOGIN}` field is not `-`) and the User-Agent is not `sonarqube-idle-check`.
- **Busy CE**: `GET /api/ce/activity_status` (called by the idle checker as `admin`, with User-Agent `sonarqube-idle-check`) succeeds and reports `pending > 0` or `inProgress > 0`. A failed call counts as not busy.
- **SSM parameters** (all SecureString): `/sonarqube/db-password`, `/sonarqube/admin-password`, `/sonarqube/tunnel-token`, `/sonarqube/wake-key`, `/sonarqube/jwt-secret`.
- **Heartbeat**: while a scan runs, a background loop sends `GET <base URL>/api/users/current` with `Authorization: Bearer <token>` every `SONAR_HEARTBEAT_SECONDS` (default 300). The token goes to curl through a config on stdin (`curl -K -`), never in argv. SonarQube authenticates each call, so each one counts as activity.
- **Keychain items** (generic passwords, account `$USER`): service `sonarqube-analysis-token` (the global analysis token) and service `sonarqube-wake-key` (the wake key).
- **Project key**: the repository name. For a local checkout, it is the basename of the `origin` URL without `.git`; with no `origin`, the basename of the repo's top-level folder.
- **Default branch** (local): the target of `refs/remotes/origin/HEAD`, else `git config init.defaultBranch`, else `main`.
- **Images**: `sonarqube:26.10.0.133078-community` and `sonarsource/sonar-scanner-cli` at an exact version tag.
- **Tag**: every taggable AWS resource has `Project=sonarqube`.

### B: Worker (`npm --prefix worker test`)

- B1 GIVEN the origin answers 200 WHEN a GET, or a POST with a body, arrives THEN status, headers and body are passed through unchanged and no AWS request is made.
- B2 GIVEN the origin is down and the request carries a wake credential THEN the Worker makes exactly one POST to `https://autoscaling.us-east-1.amazonaws.com/`:
  - form body: `Action=SetDesiredCapacity`, `AutoScalingGroupName=sonarqube`, `DesiredCapacity=1`, `HonorCooldown=false`, `Version=2011-01-01`
  - an `AWS4-HMAC-SHA256` Authorization header scoped to `us-east-1/autoscaling`

  It then answers 503 with `Retry-After: 30` and JSON body `{"status":"WAKING"}`.
- B3 GIVEN the origin is down and the request carries no wake credential THEN the Worker answers 503 with `Retry-After: 30` and `{"status":"DOWN"}`, and makes no AWS request.
- B4 GIVEN the origin is down, the request carries a wake credential and the AWS request fails or throws THEN the Worker answers 503 with `Retry-After: 30` and `{"status":"WAKE_FAILED"}`, and logs the failure with `console.error`. The log never includes credentials, keys or cookies.
- B5 GIVEN the origin is down THEN each of these counts as no wake credential (B3 applies):
  - an `Authorization` header alone, valid-looking or not
  - a wrong, empty or truncated `X-Sonar-Wake-Key`
  - a `JWT-SESSION` with a bad signature, a modified payload, `alg` other than `HS256` (including `none`), a missing `exp`, an `exp` in the past, or a value that isn't a JWT
- B6 GIVEN any request THEN the Worker fetches the origin at most once, and forwards the request without adding or removing headers.
- B7 The SigV4 signature for a fixed date, key and body matches a known-good vector checked into the tests.
- B8 A JWT signed by the tests with a known session key, valid `exp` and `alg` `HS256` is accepted as a wake credential.

### C: Idle checker (`python3 -m unittest discover -s instance/tests`)

- C1 GIVEN activity within the last 30 minutes THEN not idle.
- C2 GIVEN no activity in the last 30 minutes, a CE that isn't busy and uptime of at least 30 minutes THEN idle. "No activity" here means every recent line has `LOGIN` `-`, or the `sonarqube-idle-check` User-Agent, or falls outside the window.
- C3 GIVEN no activity but a busy CE THEN not idle.
- C4 GIVEN uptime under 30 minutes THEN not idle, whatever the log says.
- C5 GIVEN idle THEN the checker runs exactly one command, `aws autoscaling set-desired-capacity --auto-scaling-group-name sonarqube --desired-capacity 0 --no-honor-cooldown --region us-east-1`. It stops no service.
- C6 GIVEN not idle THEN the checker runs no command.
- C7 GIVEN idle and the `aws` command exits non-zero THEN the checker exits non-zero having run nothing else. A second run with the same inputs runs the same `aws` command again.
- C8 GIVEN the CE call fails (connection refused, a timeout or a non-200 status) THEN the CE counts as not busy.

GIVEN no `UP` within `SONAR_WAIT_SECONDS` (default 900) THEN it exits non-zero.

- F2 GIVEN mock secret values THEN the rendered user data contains none of them.

## Decisions

- 2026-10-26: OpenTofu owns every AWS and Cloudflare resource. State lives in a versioned S3 bucket with native locking, applied from the user's Mac with their SSO session.
- 2026-10-26: A Cloudflare Worker on H is the watchdog. When the origin is down, it sets the group's desired capacity to 1 and answers 503 with `Retry-After`.
- 2026-10-26: The Worker authenticates to AWS with an IAM user's access key, stored as a Worker secret and limited to `SetDesiredCapacity` on the group. Describe is not needed.
- 2026-10-26: Cloudflare Tunnel connects the origin. There are no inbound ports on the instance.
- 2026-10-26: Spot only. The cheapest x86 types with 2 vCPU and 4–8 GiB are `t3.medium`, `t3a.medium`, `t2.medium`, `t3.large`, `t3a.large` and `c7i-flex.large` ($0.014–0.034/h on 2026-10-26). x86 keeps a single AMI. Capacity rebalancing is off, so two instances never share the tunnel and the database.
- 2026-10-26: The database is Aurora Serverless v2 PostgreSQL 17.x with auto-pause at 0 ACU, and the instance is stateless. Deletion protection and a final snapshot guard the data.
- 2026-10-26: The service scales to zero. The instance checks every 5 minutes, and after 30 minutes with no activity and an idle CE, it sets the group to 0.
- 2026-10-26: Local scans use the same project as CI and run only on a clean default branch. The reusable workflow runs only on the default branch too.
- 2026-10-26: One global analysis token, kept in the macOS Keychain and set as each repo's `SONAR_TOKEN` by `scripts/onboard.sh`. Projects are created on their first analysis.
- 2026-10-26: Shell access is through SSM Session Manager only.
- 2026-10-26: A $10/month AWS Budget on tag `Project=sonarqube` emails `aws@sebastiansuarez.dev`.
- 2026-10-26: This repo is public on GitHub as `sebastian-suarez/sonarqube`, so public and private repos can both call the workflow.
- 2026-10-26: Confirmed by the user. Secrets go in SSM Parameter Store SecureString (free) instead of Secrets Manager ($0.40 per secret a month). SonarQube and scanner images are pinned to exact tags, and upgrades are manual (bump the tag, apply, then run `POST /api/system/migrate_db`).
- 2026-10-26: Confirmed by the user. Activity counts only requests from signed-in callers, so crawlers can't keep the service running. After the attack, this is implemented as access-log lines that SonarQube itself authenticated, replacing the Worker's activity header.
- 2026-10-26, attack finding 1, accepted: the instance role uses a narrow inline Session Manager policy instead of `AmazonSSMManagedInstanceCore`, which grants `ssm:GetParameter*` on `*` (verified on the managed policy's current version).
- 2026-10-26, attack finding 2, accepted: the idle checker only calls `set-desired-capacity 0`, and the services stop through the OS shutdown on termination. A failed call leaves everything running for the next run to retry, and a failed CE call counts as not busy.
- 2026-10-26, attack finding 3, accepted: cloudflared starts only after the admin bootstrap is verified over localhost. Otherwise ingress stays closed.
- 2026-10-26, attack finding 4, accepted: waking needs a wake credential, either the wake key or an HS256 session cookie verified at the edge with the shared session key. Setting `sonar.auth.jwtBase64Hs256Secret` also keeps browser sessions alive across cold starts. CI and the scripts send the wake key; `onboard.sh` sets it as `SONAR_WAKE_KEY`. Known limit: a session the user has logged out of can still wake the service until its `exp`, but it doesn't count as activity, so the service scales back to zero.
- 2026-10-26, attack round 2, finding 1, accepted: scans keep the service alive with an authenticated heartbeat every 5 minutes, in both `scan.sh` and the reusable workflow, so a local analysis longer than the idle window doesn't lose its server before uploading (D4, D9, E7, G7).
- 2026-10-26, attack round 2, finding 2, accepted: `onboard.sh` always refreshes the wake key from SSM into the Keychain before setting repo secrets, so rerunning it after a rotation hands out the new key (D7).
- 2026-10-26, version 2, review round 1 (task and artifact reviewers): the heartbeat endpoint changes from `/api/authentication/validate` to `/api/users/current`. SonarQube's `UserSessionInitializer` lists `validate` in `SKIPPED_URLS`, so it never sets the `LOGIN` access-log attribute and heartbeats never counted as activity. `/api/users/current` is not skipped, needs no permission, and accepts the global analysis token. Approved by the user.
- 2026-10-27, version 3, first live deploy: the organization's declarative policy `ec2-baseline` turned on VPC Block Public Access in `block_bidirectional` mode on 2026-10-27 at 00:04 UTC, with exclusions allowed. The instance lost all internet egress, so it could not reach SSM, dnf, Docker Hub or the Cloudflare edge, and never booted SonarQube. An `allow-egress` exclusion was proposed first, but the focused attack showed it doesn't work for this topology. AWS's VPC BPA advanced example (scenario 6) blocks a public-IP instance behind an internet gateway even with an egress-only exclusion: those exclusions only cover NAT gateways and egress-only internet gateways. A NAT gateway costs about $33 a month, against a $10 budget, and an IPv6 egress-only path would need a redesign (GitHub has no IPv6). Each public subnet therefore gets an `allow-bidirectional` exclusion, restoring the posture the design had before the policy. Inbound stays closed by the instance security group, which has no ingress rules (A7), and by SonarQube binding only to localhost behind the outbound-only tunnel (F1, F3). The private subnets stay under Block Public Access. The organization policy itself stays unchanged (out of scope). Approved by the user.
- 2026-10-27, version 4: the stack moves from the organization's management account to a dedicated member account `sonarqube` (`368861736633`, OU `Workloads`, root email `sonarqube@aws.sebastiansuarez.dev`, SSO access for the `Admins` group through `AdministratorAccess`, IAM access to billing denied). The first deploy went to the management account only because the default profile points there. The user wants one account per project, and AWS advises against running workloads in the management account. Every OpenTofu root pins `profile = "sonarqube"` and `allowed_account_ids`, and `onboard.sh` and the README commands pass `--profile sonarqube`, so a missing profile fails instead of falling back. The `Project` cost allocation tag can only be activated by the management account, so it leaves the stack. It was removed from the old state before teardown and stays active for the whole organization, which keeps the budget's tag filter working. A tag-based Resource Group `sonarqube` (`Project=sonarqube`) groups the resources in the console. The old stack, its state bucket and its final snapshot were destroyed (only one test analysis was lost). Approved by the user.
